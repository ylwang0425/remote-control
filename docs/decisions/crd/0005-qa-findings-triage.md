## 裁决一：D1–D6 全部**暂不改代码**，记录在案

**理由（三条，按权重）**：

1. **root 正在部署当前二进制**。改 relay 源码会产生**新哈希**，让 `EDFE6BA2…` 作废，服务器要再走一次
   "核对哈希 → 覆盖 → 重启 → 自检"。为"错误码字符串不完全一致"付这个代价不划算。
2. **没有已发布的客户端依赖这些差异**。手机端与桌面端都不区分 `invalid_json` / `invalid_request`
   （两者都是 HTTP 400，且手机只在"配对失败"这一层做中文提示）。
3. **D2 不是实现缺陷，是契约自身两个数值互相压住**（见下），改实现也修不掉。

| # | 级别 | 内容 | 裁决 |
| --- | --- | --- | --- |
| **D1** | optional | `{"method":123}`（类型错）返回 400 **`invalid_json`**，而契约 §7.3 表写 **`invalid_request`**。状态码一致，机器码不同 | **记录，不在本轮改**。若日后因别的原因再次改动 relay 源码，**顺手折进这次修复** |
| **D2** | optional | 契约 §7.3 的 **`too_long` 在 HTTP 面上不可达**：`params.text` ≥16385 时 body 先撞 §5.4 的 16384 上限 → 先回 413 `payload_too_large` | **记录为契约内部数值冲突**（已落 `qa/gaps.md` 的 GAP-8）。**本轮不改数字** —— 调整它属于契约变更，且没有用户可见收益 |
| **D3** | optional | 未知路径 `POST /api/xxx` 返回 **405 `method_not_allowed` + `Allow: GET, HEAD`**，而契约 §5.5 散文写"未知路径 → 404 `not_found`" | **记录为契约散文与实现不一致**。QA 已正确指出：该路径上**确实存在** GET 端点（`pageHandler`），所以 405 可能才是真实语义。修契约散文比修实现更可能正确，但**留到下次动契约时一并处理** |
| **D4** | note | `/downloads/....//relay.json` 被 mux 的路径清理以 **307** 拦在 handler 之前；**没有服务任何文件**（QA 实测确认） | 记录。**不是安全缺口**，只是"所有拒绝都是同一句 `not found`"这句话在路由器这一层不成立 |
| **D5** | note | `hello.ok` 的 `maxPending` 写死 16，不读配置（当前默认恰好也是 16，看不出差别） | 记录。与 S4"删除死开关"方向一致，下次一并处理 |
| **D6** | note | 若干 `message` 文案与契约 §7.3 表不一致 | 记录。契约只钉 `code`、不钉 `message`，**不算违规** |

## 裁决二：**G2 的根因更正**（这是本 CRD 最重要的一条）

**原记录**（relay 工程师）：`pair.used` 丢失的根因是"桌面在 `pair.create` 与手机配对之间**重连**过，
原连接已不存在，`Hub.Send` 返回 `ErrSendFailed`，而 `notifyPairUsed` 丢弃了返回值"。
工程师自己已注明这是**推断**（"我没有重现 QA 的真实环境"）。

**QA 的实测结论（12/12 通过的那一轮）**：在**单 socket、全程未断连**的复现里，`pair.used`
**能正常到达**，且是配对后的**第一帧**。因此：

> **"桌面重连"这个根因在 QA 的复现里不成立，无法证实它是真根因。**

**QA 还主动交代了一种更可能的解释**：它自己早期的 harness 里写过一句
`b.ReadType("request", 3*time.Second)` 用来 drain 请求帧，`pair.used` 恰好在那个窗口到达，
**被当作未知帧读掉并丢弃**，于是看起来完全像"产品从不发送"。也就是说：
**当时那个"症状"本身有可能是 QA harness 的假象。**

**PM 裁决**：

- **症状确已消失**（QA 现测能收到），但**根因未经复现**。凡引用此事，一律写成
  **"症状已消失；根因未复现（原因为推断）"**，不得写成"根因已确认并修复"。
- **`broadcast` / `hub.Pick()` 的改法本身保留**，理由与 QA 一致：契约 §8.1 明确允许同一
  `bridgeToken` 存在多条连接（重连窗口内新旧并存），而 §8.4.6 要求把 `pair.used` 交给
  "签发该 code 的桌面"；当 owner 连接已消失时，广播是**唯一**能让桌面知道"有人配对了"的做法。
  所以它是一条**有价值的防御性改进**，即使它修的不是当初那个原因。
