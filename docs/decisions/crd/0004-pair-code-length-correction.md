# CRD 0004 — 配对码长度自相矛盾（20 vs 24）的更正

> 撰写：PM ｜ 日期：2026-10-08 ｜ 状态：**accepted（PM 决定：这是"更正"，不是范围变更）**

## 谁提出的

`crew_engineer`（T-mobile），通过 `C:\Users\Hi\.dsh\crew\jobs\ai-remote-deliver\inbox\Q-01.md` 上报。**它没有改动契约一个字节**，只是上报并给了三个选项与一个不阻塞的临时读法。

## 他们看到什么

`docs/design/api/protocol-v1.md` §4.6 与 §7.2 里，**同一句话出现两个数字**：

| 依据 | 归一化后字符数 |
| --- | --- |
| 正则 `^[0-9A-HJKMNP-TV-Z]{4}(-[0-9A-HJKMNP-TV-Z]{4}){5}$` | **24**（6 组） |
| 例子 `K7QP-3MZD-9XTB-2RCV-6HNF-0JWS` | **24**（6 组） |
| 散文「20 字符」「20×5 bit = 100 bit 熵」 | 20 |
| 散文「总长 29 字符（含 5 个 `-`）」 | 29 − 5 = **24** |

**唯一可机器执行的产物（正则）与唯一的具体例子都写 24**；散文里的"20"出现 3 次（§4.6 两次、§7.2 一次）。两侧工程师各拿一个数字实现，配对会永远失败，而两边各自的单元测试都是绿的。

## 为什么这不是"范围变更"

用户 brief 只要求"**一次性高熵 code 至少 10 字符 / 5 分钟 / 限速 / 单次消费**"。20 与 24 **都满足**≥10 字符，所以**两条读法都不改变用户可以看见的行为** —— 没有新增或删除任何功能、端点、方法或字段。因此这是**更正**（一份自相矛盾的契约被改成只剩一个数字），不是范围变更；但它动的是**接口契约**，所以按规则写成 CRD 并由架构角色执行。

## 我查了什么（先看，再问）

1. **relay 侧还没有实现配对码生成**：`relay/` 当前只有 `internal/config/`、`internal/protocol/errors.go`、`internal/protocol/origin.go` —— 没有 code 生成器。**所以选任何一个数字都不会让已完成的代码作废**（这是本裁决最贵的那个风险，已排除）。
2. **mobile 侧已经按"超集"实现**：`mobile/web/js/core.js` 里 `PAIR_ACCEPTED_LENGTHS = [20, 24]`，并注释写明了矛盾。**两个读法都不会把用户挡在门外**（这是工程师做对的地方，值得保留）。
3. 用户 brief 的下限是"至少 10 字符" → 两个数字都合规。

## 决定

**选项 A：以正则与例子为准 = 归一化后 24 个 Crockford 字符（6 组，总长 29 字符含 5 个 `-`，120 bit 熵）。**

理由，按权重排序：

1. **正则与例子是"会被复制的东西"。** 顺序是：架构师写正则 → 工程师把正则抄进代码 → 测试锁住它。散文里的"20"不会被任何人抄进代码。改散文的风险最低。
2. **熵更高**（120 bit vs 100 bit），在"至少 10 字符高熵"这条要求上更稳。
3. **不动正则 = 不给未来的实现留下"曾经有两个数字"的记忆负担**；例子也一个字不用改。

**选项 B（改成 20，改正则与例子）被驳回**：它动的是那个最容易被复制的产物，且熵更低。**选项 C（不裁决）被驳回**：那等于放弃这条边界，配对会随实现漂移。
